{{ icon('home') }} Home Assistant app

The easiest route: one install, updates through Home Assistant, and secure remote access with no ports to forward.

{{ icon('info') }}
Add-ons require Home Assistant OS or Supervised. If you're on Container or Core, use the Docker route below — it's the same app.
  1. Add the repository. In Home Assistant go to Settings → Apps → Install App, open the ⋮ menu (top right), choose Repositories, click 'Add' and paste the URL below, then click Add again. 
    {{ site.ha_repo }}
  2. Install. Close the dialog, find My Kitchen in the store and click Install. The first build clones the app and builds an image locally, which takes a few minutes on a Pi.
  3. Configure. On the Configuration tab, set your LLM provider and API key (see Configuration below). Save.
  4. Start. On the Info tab, click Start. Turn on Show in sidebar for convenience.
  5. First login. Open the add-on. A starter account is created automatically and its password is printed once in the add-on Log tab (Apps → My Kitchen → Log). Log in with those details, then change the password in-app under Household.
{{ icon('info') }}
Remote access. With Home Assistant Cloud (Nabu Casa) or your own HTTPS, the add-on is reachable securely through HA ingress. No ports to forward and nothing exposed directly to the internet.

{{ icon('cooking') }} Setting up your kitchen

Installed and logged in? A quarter of an hour spent here is what makes the app useful rather than empty. Roughly in this order:

  1. Change the starter password and add everyone else in the house, under Household.
  2. Add dietary tags for whoever needs them — allergies, disliked foods, diets — and assign them to people as you create them. A tag assigned to nobody never reaches a recipe.
  3. Prune the catalogue. A fresh install seeds around 170 common ingredients to save you typing. Under Manage → Ingredients, retire the ones you'll never buy and add the ones you always do. This is the one bit worth doing properly — everything else is built on it.
  4. Check your staples. Anything you always have — oil, salt, common spices, flour — should be flagged as a staple so it stays out of your stock list and gets used freely.
  5. Add your equipment under Manage, so recipes are written for the kitchen you've actually got.
  6. Set your stock — a first pass through the kitchen, checking in what's there.
  7. Cook something. Hit Lets Cook. Your suggestions will be empty at first; that list fills out as your recipe bank grows, and writing in two or three recipes you already cook regularly is the fastest way to get it going.

{{ icon('dns') }} Docker

My Kitchen is a single container with a single-file SQLite database on a mounted volume, and it runs database migrations automatically on start.

  1. Clone the repo. 
    git clone {{ site.github }}.git
cd my-kitchen
  2. Set your config. Copy the example environment file and fill in your values. At minimum, a stable SECRET_KEY, your LLM provider and API key, and the database path. The repository's DEPLOY.md lists every variable. 
    # a few of the key variables (see DEPLOY.md for the full list)
SECRET_KEY=change-me-to-a-long-random-string
MY_KITCHEN_DB_PATH=/data/my_kitchen.db
LLM_PROVIDER=gemini
APP_TIMEZONE=Europe/London
  3. Launch. 
    docker compose up -d --build
  4. Reverse proxy (optional). Put it behind nginx or Caddy for a clean hostname and TLS.

{{ icon('tune') }} Or just run it

It's an ordinary Flask app, so no container is required if you'd rather not.

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # then edit
flask db upgrade && flask seed  # schema + starter catalogue
python run.py

With LLM_PROVIDER=mock that needs no API key at all — a good way to click through the whole app before deciding whether you want it.

Configuration

My Kitchen talks to a large language model through a swappable provider adapter. Set these in the app's Configuration tab, or as environment variables under Docker.

SettingWhat it doesDefault
LLM providerWhich model service to use: gemini, anthropic, or mock (no API calls — for trying the app).gemini
API keyYour key for the chosen provider. Stored on your device; sent only with generation requests.—
ModelThe specific model to call.gemini-3.5-flash
TemperatureHow adventurous generation is. Higher = more variety.0.8
Max tokensOutput length ceiling per generation.8000
TimezoneUsed for recipe history timestamps.Europe/London

What it costs

The app is free and open source. The running cost is your provider's API usage, billed to your own key. Only generation calls the model — browsing, suggestions, stock and everything else are local and free — and a generation is a single call to a lightweight model. In practice that's pennies over a month of normal household cooking, but it isn't nothing, and it's worth setting a spending cap in your provider's console.

{{ icon('info') }}
Running fully local? Not yet. The provider adapter is deliberately swappable and a local model (such as Ollama) is a natural fit for it, but that provider isn't written — today, generation means a hosted model and an API key. See Privacy & data.

Updating & backups

Home Assistant: new versions appear under standard 'updates'. Configure Settings → System → Backups so HA snapshots the add-on before schema-changing releases.

Docker: git pull then docker compose up -d --build; migrations apply on start. Your data lives on the mounted /data volume. Back that up yourself however you want.

What changed in each version is listed under Releases.
